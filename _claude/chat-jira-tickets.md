# ჩატის სისტემა — Jira ტიკეტების ბექლოგი

აღებულია `chat-auto-assign-plan.md`, `chat-reporting-plan.md`,
`chat-supervisor-ui-plan.md`, `chat-dashboard-ui-plan.md` და
`chat-requirements-coverage.md`-ში ნაპოვნი ხარვეზებიდან. ორგანიზებულია
Epic → Story/Task სახით, პირდაპირ Jira-ში ჩასასმელად. Repo სვეტი გვიჩვენებს
რომელ კოდბაზას ეხება ტიკეტი: **BE** = `Enterprise_Georgia_Backend`,
**FE** = `Enterprise_CMS`.

Epic 1-4-ს უკვე აქვს დეტალური plan-დოკუმენტი (მითითებულია) — შეიძლება პირდაპირ
შეფასდეს და დაიწყოს. Epic 5-8 ეხება დადასტურებულ ხარვეზებს, მაგრამ **ჯერ არ
აქვთ დეტალური გეგმა** — მოეპყარით როგორც "დაპროექტება + იმპლემენტაცია"
ტიკეტებს, ან თითოეულის პირველი ტიკეტი გამოყავით spike-ად.

### დეტალური აღწერები (Jira "Description" ველისთვის)

**0.1 — ერთიანი სქემის მიგრაცია**
ბექენდის Prisma სქემაში (`prisma/schema.prisma`) ერთდროულად უნდა დაემატოს
ყველა ის ცვლილება, რომელიც ცალკეულ Epic-ებში ცალკე იყო მოთხოვნილი: ახალი
`Program` მოდელი (`id`, `name`, `isActive`, timestamps), `ChatSession`-ზე სამი
ახალი ველი — `region` (სტრიქონი), `programId` (`Program`-ზე მიმართვა) და
`firstResponseAt` (თარიღი/დრო), და `CannedResponse`-ზე ახალი `category` ველი.
მთავარი მიზეზი, რატომ უნდა გაერთიანდეს ერთ მიგრაციაში: თუ თითოეული Epic
თავისი მიგრაციით წავა, იგივე ცხრილები (`chat_sessions`, `canned_responses`)
რამდენჯერმე შეიცვლება, რაც ზრდის კონფლიქტისა და გამორჩენილი ველის რისკს.
შედეგად უნდა მივიღოთ ერთი `prisma migrate dev` გაშვება, რომელიც ამზადებს
ნიადაგს Epic 1, 2 და 8-ისთვის ერთდროულად.

**0.2 — ChatService-ის გაფართოება, როგორც ცენტრალური data-access ფენა**
`chat.service.ts` უნდა გახდეს ის ერთადერთი ადგილი, საიდანაც სხვა ყველა
ფუნქციონალი კითხულობს ჩატის მონაცემებს. საჭირო დასამატებელი მეთოდები:
`getActiveCountsByOperators(operatorIds)` და `getNextQueuedSession()`
(გამოიყენება Epic 1-ის ავტო-მინიჭებაში), `getActiveSessionCount(operatorId)`
(ხელით მინიჭების ლიმიტის შემოწმებისთვის), და ანგარიშგების ბაზისური
აგრეგაციები (`getOperatorStats`, `getOverviewStats`, `getRegionProgramReport`,
`getWorkloadSnapshot` — Epic 2-დან). ეს ტასკი პრიორიტეტულია, რადგან Epic 2, 3
და 4 ყველა უშუალოდ ამ მეთოდებს იძახებს — თუ აქ ინტერფეისი არასწორად
დაპროექტდება, გადაკეთება მოგვიწევს სამივე დამოკიდებულ ეპიკში.

**0.3 — ChatGateway-ის გაფართოება, როგორც რეალურ დროში ქცევის ბირთვი**
`chat.gateway.ts` (Socket.IO gateway) არის ერთადერთი ადგილი, სადაც ხდება
რეალურ დროში ყველა მოვლენა: ვიზიტორის ჩატის დაწყება, ოპერატორის შეტყობინება,
ჩატის დახურვა. აქ უნდა დაემატოს Epic 1-ის ავტო-მინიჭების ლოგიკა
(`pickAvailableOperator`, `tryAssignSession`, `drainQueue`, 3-ჩატის ლიმიტის
შემოწმება), მოგვიანებით კი Epic 5-ის ოპერატორის სტატუსის ცვლილებების
გავრცელება (`operator:status_changed` ტიპის მოვლენები) და Epic 6-ის
უმოქმედობის ტაიმერები (setTimeout/interval თითოეულ აქტიურ სესიაზე,
გაფრთხილება + ავტო-დახურვა). ვინაიდან ეს ფაილი ბევრ ეპიკშია ჩართული, ღირს
თავიდანვე კარგად სტრუქტურირება (ცალკე დამხმარე მეთოდები თითოეული პასუხისმგებლობისთვის), რომ არ გადაიზარდოს მართვად შეუძლებელ "ღვთის ობიექტად".

**0.4 — ელფოსტის გაგზავნის მოდულის დამატება**
ამჟამად ბექენდში (`Enterprise_Georgia_Backend`) საერთოდ არ არსებობს
`mail`/`email` მოდული — ეს დადასტურებულია კოდის სრული ძიებით. ეს ბლოკავს
მთელ Epic 6-ს (საკონტაქტო ფორმა → `info@gedc.ge`, არასამუშაო საათების
შეტყობინება, შესაძლოა უმოქმედობის გაფრთხილების დუბლირება მეილზეც). საჭიროა:
(1) provider-ის არჩევა (მაგ. SMTP/Nodemailer, ან cloud provider — SES/SendGrid
და ა.შ., გუნდის არსებული ინფრასტრუქტურის მიხედვით), (2) მინიმალური
`MailService`-ის შექმნა ერთი მეთოდით — `send(to, subject, body)` — რომელიც
შემდეგ Epic 6-ის ყველა ცალკეულ ტიკეტს შეუძლია გამოიყენოს ხელახლა კოდის
დუბლირების გარეშე. რეკომენდებულია ეს ტასკი Epic 6-ის დაწყებამდე დასრულდეს,
რომ არცერთი Epic 6-ის ტიკეტი ცალკე spike-ად არ დარჩეს.

**0.5 — `chat.reports` უფლების დამატება**
ანგარიშგებისა და დაშბორდის endpoint-ები (Epic 2, Epic 4) არ უნდა იყოს
ხელმისაწვდომი ჩვეულებრივი ოპერატორებისთვის — მხოლოდ ადმინისტრაციისთვის,
რადგან ეს მონაცემები აჩვენებს ოპერატორთაშორის შედარებას (ვინ რამდენ ჩატს
ამუშავებს, ვისი შეფასება უფრო დაბალია და ა.შ.). საჭიროა ახალი უფლების
გასაღების დამატება ორივე მხარეს: ბექენდში `RequirePermissions('chat.reports')`
დეკორატორი ახალ endpoint-ებზე, და CMS-ის მხარეს `permissions.ts`-ში
შესაბამისი კონსტანტა (`CHAT_REPORTS: "chat.reports"`), რომ `usePermission`
hook-მა UI-ც სწორად დამალოს არაუფლებამოსილთათვის. ეს ერთხელ კეთდება და
შემდეგ Epic 2 და 4-ის ყველა endpoint/კომპონენტი მას იყენებს.

**0.6 — ჩატის საერთო UI ფენის მომზადება**
CMS-ის მხარეს (`Enterprise_CMS`) სამი ფაილი — `ChatSessionList.tsx`,
`VisitorInfoPanel.tsx` და `useChatSocket.ts` — არის ის საერთო საფუძველი,
რომელსაც Epic 3 (სუპერვაიზორის ხედვა, დატვირთვის ბეჯები), Epic 5 (ოპერატორის
სტატუსის ინდიკატორი) და ნაწილობრივ Epic 6 (მოლოდინის შეტყობინების ჩვენება)
ეყრდნობა. ამ ტასკის ფარგლებში ასევე ემატება `apexcharts` და
`react-apexcharts` დამოკიდებულებები `package.json`-ში (გადმოტანილი
`Growthhub_Crm`-ის analytics მოდულიდან — იხ. `chat-dashboard-ui-plan.md`),
რომ Epic 4-ის chart-კომპონენტების პორტირებას საფუძველი ჰქონდეს. რეკომენდაცია:
ეს ტასკი შესრულდეს მცირე, დამოუკიდებელ commit-ებად თითოეული ფაილისთვის, რომ
მოგვიანებით Epic 3/5/6-ის ცვლილებები არ დაეჯახოს ერთმანეთს ერთსა და იმავე
ფაილებზე.
